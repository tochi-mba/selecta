## What is implemented

- Device-local, no-installer two-deck Web Audio graph: decoded `File` -> `AudioBufferSourceNode` -> per-deck gain -> low/high shelf EQ -> **two-input AudioWorklet** -> dynamics compressor -> master gain -> default system output.
- Standard Web Audio decoding for authorised local selections, with the current and next recording in a bounded two-buffer cache; no audio upload, signed Cloud media URL, playback proxy, Python process or FFmpeg invocation.
- Play, pause, resume, stop, seek, next, previous, equal-power baseline crossfade, volume, fade duration and ±12 dB low/high shelves. Transition preparation/decoding and control scheduling run outside the audio callback; the worklet uses a bounded, allocation-free stereo/monaural sum and clamp.
- Live transport state including index, current track, progress, AudioContext status, command preparation, generation, tab ownership and recoverable error.
- One-origin audio ownership: Web Locks exclusive across browser tabs/PWA windows where supported. On older browsers, BroadcastChannel + short-lived origin-storage lease is **cooperative, not atomic**. Playback fails closed where no coordination is possible. Duplicate tab takeover requires explicit operator confirmation.
- React StrictMode-tolerant runtime registry, engine lifecycle disposal, pagehide stop, foreground-only mobile interruption, context suspension handling and output-device-change caution. Hardware media buttons use MediaSession where supported.
- Cloud transport dock shows **Play on this browser** first, with a user-selected file picker and mobile-sized controls. Existing Cloud remote controller is opt-in, preserving protocol separation.
- Output *signal* is not asserted to be physical audibility. User must acknowledge hearing the intended output; change/focus/interruption/stop invalidates the assertion.

## Playback, buffering and recovery semantics

- A deliberate tap/click invokes `AudioContext.resume()` before asynchronous work. A successful resume does not mean a physical speaker is audible.
- A file larger than the in-memory admission cap is rejected clearly (48 MiB on detected low-memory devices, otherwise 96 MiB); this initial implementation uses whole-file `decodeAudioData`. No claim of a long-set, windowed streaming decoder yet. Native decoder support varies across browsers.
- The next recording is opportunistically decoded while the active one plays; failure to decode the next file does not immediately stop the current one.
- A main-thread timer schedules a baseline equal-power transition just before the track ends, and `onended` provides a fallback path. Suspended/hidden browsers may miss timing; they are explicitly interrupted rather than silently claimed alive.
- Pause releases tab ownership. Stop resets local playback and audible confirmation. A hidden page or an unexpected suspended context requires a fresh user gesture; audio is **never silently restarted** after an OS/browser interruption.
- System output is selected by the OS. `setSinkId`, AirPlay, Bluetooth/USB routing and multi-zone are not claimed uniformly supported, especially on Safari/iPadOS.

## Known limitations and blockers

1. Large/long recordings need Agent 02+03 bounded/windowed decode, resampling, sample-rate/route-change verification and memory/latency measurement. This baseline rejects oversize files; full-file decoding is not suitable for a six-hour venue playlist without future optimisation.
2. No time-stretch, beat sync, stem inference, neural model or streaming FLAC export is claimed. The baseline crossfade is genuine and independently useful.
3. Browser Web Locks is the strongest tab-fencing mechanism; fallback lease cannot guarantee gap-free atomic exclusivity. A tab cannot fence a different physical speaker or an offline device.
4. Network-connected remote devices remain managed through the opt-in existing `LocalFirstPlayer` and its metadata-only Cloud API; there is no fabricated bridge equating browser-local audio with a registered Cloud device.
5. Real phone/tablet foreground tests, six-hour powered iPad venue soak, Bluetooth disconnect, silent WebKit, battery/storage/thermal, screen lock and all codec/device matrices remain mandatory ADR-0485 release gates.
6. Background/locked-screen music, automatic reboot resume, independent tablet multi-zone output and storage persistence are explicitly not promised.
7. Current E2E config matches `*.e2e.ts` and starts a Python server; Agent 10 must register this dedicated `*.spec.ts` Vite browser suite in its owned Playwright configuration before it can be reported executed.

## Manual acceptance route

Open Cloud with `local_first.player_v1`, select two local WAV/MP3 files and tap **Tap to start audio**. Verify gain, crossfade and seek; confirm sound *physically*, then pause and use a second tab to request an explicit handoff. Repeat on Android Chrome, iPad Safari/PWA and desktop Safari/Firefox, recording device, OS, browser, file format, decoder result, actual output, interruptions and any false audible indication. Do not use a Python server to provide the music.
