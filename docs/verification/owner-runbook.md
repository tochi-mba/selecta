# Owner verification runbook

Every open checklist task in `docs/adr/*-implementation-checklist.md` whose status says
"Needs a person" is listed here, grouped into eight sittings so that one sitting with one set
of tools closes as many tasks as possible. Code cannot close these tasks: they need your ears,
a screen reader, a real phone, a participant, a named reviewer, a lawyer or a staging account.

The task lists and trackers are generated by `python -m selecta.audit.owner_runbook --write`
from the checklists, so they never drift: when a task is ticked with evidence it drops out
on the next run. `--check` exits 1 when this file is out of date (tests/test_owner_runbook.py
runs it in CI). Never edit the generated block or the tracker files by hand.

## Order

1. Sign-off, part A (first 30 minutes): approve the decisions and study thresholds that the
   other sittings depend on (see sitting 8, step 1).
2. Sittings 1 to 4 (visual review, screen reader, devices, listening): on your own, any order.
3. Sitting 5 (user studies): needs recruited participants, so start recruiting early.
4. Sittings 6 and 7 (staging and drills, legal and business): run alongside the rest; they
   wait on accounts, advisers and replies rather than on you.
5. Sign-off, part B (last): release dispositions, once everything else has a result.

## Rules for every sitting

- Work at one exact commit. Write down `git rev-parse HEAD`, the date, the machine, the OS
  build, the browser and version, the theme and the input method before you start.
- Use the made-up library (`python tests/e2e_server.py <port>`, build the site first with
  `pnpm build` in `web/`; `SELECTA_E2E_STRESS=1` adds long, missing, duplicate and
  right-to-left names) unless a step says to use real music. With real music, run a copy of
  your home (`SELECTA_HOME` pointing at a copied folder) for anything that writes data.
- `dev.cmd` starts the local app (API on 8733, site on 5173). `dev.cmd doctor` checks the
  prerequisites. `uv run selecta flags` shows which features are on.
- Song names, listener codes and participant names stay out of the repository.
- Severity: P0 stops a release, P1 blocks unless you accept it in writing, P2 is recorded.
- Never tick a box for something you did not see yourself. Write what you saw.

## How to record a result

1. Put the result in the evidence file the checklist line names (for example
   `docs/adr/selecta-4-evidence.md` or `docs/adr/selecta-flow-implementation-evidence.md`):
   date, SHA, environment, reviewer name, outcome, and file names of screenshots, traces or
   notes.
2. Tick the checklist box and add an Evidence field that names that record, following the
   checklist's own header rules. A failure stays unticked with the finding in its status.
3. Run `python -m selecta.audit.owner_runbook --write` and
   `python src/selecta/audit/checklist_evidence.py`, then commit both.

## Sitting 1: Visual review and baseline approval

One long desk session with a good display (and a dim room for dark theme): look at every generated screenshot, approve or reject each one, and check contrast, fonts, density and states by eye. Machines made the pictures; only a person can approve them.

**Before you start:**

- In `web/`: `pnpm e2e:baseline` (main pages at phone and desktop, both themes; it never promotes a golden on its own) and `pnpm e2e:mp` (every route in `docs/adr/mp-0272-surface-inventory.json` at 11 viewports, data in `web/mp-data/mp-0272/`).
- Paired light/dark states: `pnpm exec playwright test e2e/paired-theme.e2e.ts e2e/fp-0271-paired-states.e2e.ts`; other candidates: `e2e/polish-p0132-baselines.e2e.ts`, `e2e/s3-0075-visual-regression.e2e.ts`, `e2e/s3-0051-gallery-matrix.e2e.ts`, `e2e/mp-0279-component-gallery.e2e.ts`.
- For Selecta 3.1 tasks, download the `selecta-3-1-visual-review-1` and `-2` CI artifacts for the exact head (`docs/adr/selecta-3-1-visual-review.md`).
- Pre-redesign reference: `docs/baseline/911c981/screens/*.png` and its `manifest.json`.
- A contrast checker (any colour picker that reports WCAG ratios).

**Steps:**

1. Open each image set and its manifest. For every image write accept or reject with a reason. Never bulk-accept, and never refresh goldens to make a diff go away.
2. Component states: run `dev.cmd`, open `/workshop/diagnostics` and expand the control gallery (a test build needs `VITE_SELECTA_GALLERY=1`). Check hover, focus, pressed, selected and disabled for every control in both themes, and normal and compact density.
3. Themes: set Light while Windows is Dark and the reverse; hard-reload each route in Edge and in the installed app and watch for a flash of the wrong theme and the title-bar colour.
4. Contrast: measure a sample of each text and control role in both themes (automated part: `web/e2e/mp-0275-typography.e2e.ts`, `web/e2e/fp-theme-boundaries.e2e.ts`); record every pair below 4.5:1 for text or 3:1 for edges.
5. Forced colours: Windows Settings > Accessibility > Contrast themes, then walk each route with the keyboard; planned, ready, failed and selected must still differ.
6. Content extremes: start the stress server (`SELECTA_E2E_STRESS=1`) and look at long, missing, duplicate and right-to-left names, missing art, loading, empty, failed (stop the server) and recovered states on every route.
7. Widths: 320, 375, 768, 1280, 1440, 2560 and 3840 px. Nothing overlaps or clips; lyrics and Up Next never cover the transport.
8. Scale: `python tests/scale_server.py 8821 20000 100`, then `/library` and `/mix/current/edit` (100 songs) with the inspector open while playing.
9. Fonts: repeat a few screens with the primary font unavailable (another browser or font blocked) and check icon and number alignment.
10. Motion and sensory safety: on `/listen` Stage, check flashing, brightness and lyric motion; record the screen and cancel transitions half way.
11. Browser chrome: screenshot the real Edge and Chrome toolbars and the installed app title bar with app and OS themes opposed.
12. Commit the approved `-snapshots` folders and list each approved set in `docs/adr/completion/visual-evidence.md`.

**Pass:** Every image set has a named reviewer, date and SHA; every critical state is accepted or rejected with a reason; no P0 or P1 visual defect is missing from `docs/adr/mp-0272-defect-register.md`.

**Record:** `docs/adr/completion/visual-evidence.md` plus the programme's evidence file. Review denominators for MP live in `docs/adr/mp-0299-review-denominator.md`.

Tracker: [tracker/visual-review.md](tracker/visual-review.md)

## Sitting 2: Screen-reader and keyboard session

NVDA with Edge on Windows, then keyboard only, then Narrator for a spot check. VoiceOver and TalkBack tasks need a Mac, iPhone or Android phone; do those at the end of the devices sitting if that is when the phone is to hand.

**Before you start:**

- Install NVDA; note the NVDA, Edge and Windows build numbers.
- Scripts: `docs/adr/selecta-3-accessibility.md` "Scripts for a person" (first run, playback, editing, requests, Studio, export, zoom), the six cards in `docs/research/uf-research-protocol.md`, and the journeys in `docs/user-journeys.md`.
- Made-up library with stress names (`SELECTA_E2E_STRESS=1`), the 100-song scale server for long lists, and `dev.cmd` with real audio for playback checks.

**Steps:**

1. Route pass: on every route in `web/src/router.ts` open the NVDA elements list (NVDA+F7). Headings and landmarks make sense, every control has a name, icon buttons say what they do, long names are read in full.
2. Shell: the rail announces the current page; status messages (render, export, request) are announced once, never repeated; the clock and meters stay silent.
3. Overlays: command palette (Ctrl+K), export dialog, Requests drawer, customise sheet, menus, tooltips and nested overlays. Focus goes in, Escape closes, focus returns to the control that opened it.
4. Playback on `/listen`: the song name is spoken once per change; keyboard seek works and a disabled seek says why; Stage opens, refuses fullscreen gracefully and closes with the keyboard (repeat with reduced motion on).
5. Editor `/mix/current/edit` on the 100-song server: move a song by keyboard (new position announced, focus stays on it), jump to a problem, use the whole-mix menu, switch inspector tabs.
6. Studio grid: one tab stop, arrows announce each square, Space toggles, unavailable stems say why, the lane editor works without spatial reading.
7. Library and Song Details: reading order, focus after Back/Forward and after delete; Requests search results and a 50-plus request list.
8. Lucy `/mixes/lucy`: a long streaming reply while analysis or a render runs; count interruptions.
9. Blind study `/listening`: nothing spoken names a method or renderer.
10. Keyboard only, no screen reader: the listener, creator and expert journeys from first run to export, at 100%, 200% and 400% zoom.
11. WCAG 2.2 AA: walk the criteria list (`docs/adr/adr-0388-accessibility-language-and-motion-acceptance.md`) and note each failure with route and control.
12. If a phone is available: the same core journeys with VoiceOver and TalkBack.

**Pass:** Every essential task completes without a mouse or sight of the screen, focus is never lost or trapped, and nothing chatters. Any inaccessible essential control is P0.

**Record:** One session log per assistive technology (versions, route, task, outcome, severity) in the programme's evidence file; the access reviewer signs the SHA at the end (this closes the screen-reader sign-off tasks too).

Tracker: [tracker/screen-reader.md](tracker/screen-reader.md)

## Sitting 3: Phones, touch, zoom and hardware

Real hardware: an Android phone, an iPhone, a USB drive, wired and Bluetooth audio, and an unloaded, named Windows machine for performance traces.

**Before you start:**

- Fill the reference hardware row (CPU, GPU, RAM, storage, Windows and Edge build, display scale, power mode, audio device) in `docs/adr/selecta-microinteraction-verification-protocols.md` and `docs/adr/completion/performance.md`.
- Budgets: p75 INP 200 ms, CLS 0.1, p95 frame 32 ms, no long task over 200 ms during playback, 20k search p95 500 ms (same files).
- Phone access to the local app: Android Chrome remote debugging with port forwarding (see Known gaps below).

**Steps:**

1. Scale bench on the named machine: `python tests/scale_server.py 8821 20000 100`, then in `web/` run `pnpm exec playwright test --config bench/playwright.config.ts mi-0162`; copy the `MI-0162 {...}` lines into `docs/adr/selecta-microinteraction-performance-results.md`.
2. Edge Performance and Memory traces on the same server: Library search, filter and deep pages; 100-song Editor reorder and scroll; 64-cell Studio during analysis and render; lyrics, visualiser and theme switch; background polling.
3. Under load: play a mix while analysis or a render runs, scrub quickly, type and scroll; listen for dropouts.
4. Zoom: Edge at 200% and 400% at 1280 px, 320 px reflow, and Windows Text size enlarged. Nothing focused is hidden; no two-way scroll except the Studio grid.
5. Phone: orientation, notch safe area, short landscape, the soft keyboard over the Lucy composer, Requests drawer and dialogs, mini-player and bottom navigation, touch targets at least 44 px, reorder without dragging, Studio grid touch-scroll, menus and tooltips by touch.
6. Installed app: install from Edge and Chrome (`web/public/manifest.webmanifest`), relaunch, reload a route, stop the server and reopen: it must say the backend is unavailable, not pretend to play offline.
7. Media keys and the Windows media overlay show the right song and control playback; sleep and wake with one tab playing and a second tab open.
8. Audio devices: during playback unplug and replug a USB DAC, wired headphones and Bluetooth; sound resumes on the right output.
9. Drives: add a watched folder on a USB drive in `/workshop/sources`, start a scan, unplug, replug; revoke read permission on a folder; move the music folder to another drive and relink. Analysis and drafts survive.
10. Low power: battery saver on with `SELECTA_FLAGS=app.auto_low_motion`; the page drops to low motion and the visualiser stops when hidden.
11. Cloud device tasks (Play here transfer, guest Rooms on old phones, lid close on flaky Wi-Fi) need the staging Cloud from sitting 6; do them then.

**Pass:** Numbers within budget (or a written exception) with the machine named and raw trace files linked; no lost input, no audio dropout or double audio, nothing critical covered on any phone.

**Record:** `docs/adr/completion/performance.md`, `docs/adr/selecta-microinteraction-performance-results.md` and the programme's evidence file, each with device, browser, SHA and trace file names.

Tracker: [tracker/devices.md](tracker/devices.md)

## Sitting 4: Listening session

Your real library, good speakers or headphones, and about two hours. You judge transitions, audio ownership and exports by ear; nobody else can.

**Before you start:**

- Read `docs/listening-procedure.md`.
- Start `dev.cmd` on a copy of your home; have a screen recorder that captures system audio for the sync checks.

**Steps:**

1. Transitions: build a mix from Selecta's pick, open `/listen`, press "Jump to the transition" on at least ten different moves, rate each Good or Bad; read them back with `uv run selecta ratings` (`--json` for raw). Judge cuts, blends, wordplay and stem treatments; note when the next song really takes over and whether the visual handoff matches.
2. One sound at a time: while the main mix plays, start previews from the inspector, Studio solo, harmonic audition on `/discover/harmonic`, a request bridge preview and a Lucy approval on `/mixes/lucy`; move between routes, switch theme, open Stage, open a second tab, start a render. Exactly one source sounds and the main mix resumes where it was.
3. Studio with real stems: audition each cell and solo combination, leave mid audition, apply, and try a corrupt stem (the control is disabled, no noise). What you hear matches the technique the inspector shows.
4. Requests: request a song mid-mix; it joins with no overlap or gap. Try "Play it anyway" on a rough transition.
5. Sync: screen-record `/listen` with system audio and step through the countdown, lyrics and transition scene against the audible handoff.
6. Export: Edit > Download audio, then play the FLAC against the live mix. Check order and content with `python tests/check_export_audio.py report.json export.flac one.flac two.flac`, then listen to a set of its transitions.
7. Blind comparison: register pairs with `uv run selecta listening-import <manifest.json>`, run them on `/listening` (A/B labels give no hint of method), report with `uv run selecta listening-report <study>`.
8. Long session: leave Stage up with Focus lyrics on for a while; note anything that pulls attention from the music. Record delight 1 to 5 apart from correctness.
9. After the Cloud migration lands: repeat the transition check to confirm local transitions sound the same.

**Pass:** No unexpected gap, overlap, double preview, stale resume or drift; the FLAC matches the frozen draft; the bad-transition share (rated 2 or lower) is reported as a share, not a mean, and kept apart from test results.

**Record:** Per-transition notes and the bad-transition share in the programme's evidence file and `docs/acceptance.md` under a dated heading. No song names in the repo.

Tracker: [tracker/listening.md](tracker/listening.md)

## Sitting 5: User-study sessions

Watching other people use Selecta without help: listeners, creators, DJs and novices. Several sessions of about an hour each; the tasks are bundled so every participant covers several blocks.

**Before you start:**

- Sign the study thresholds first (sitting 8, part A, including UF-0367-04 and SF-0198-07).
- Protocols: `docs/research/uf-research-protocol.md` (cohorts, cards U1 to U6, measures), `docs/research/flow-research-protocol.md` (listener cards L1 to L5, creator cards C1 to C6, five-second tests), `docs/adr/selecta-3-baseline.md` "Task scripts", `docs/adr/selecta-experience-acceptance.md`, and the MI-0164-04 list in `docs/adr/selecta-microinteraction-verification-protocols.md`.
- Recruit three cohorts (listeners, creators, expert DJs); dry-run the cards with a colleague.
- Fresh state per participant: `python tests/e2e_server.py <port>` in a fresh browser profile. Real music only where a task says so.

**Steps:**

1. Five-second tests: show Explore, Create, Listen, Library and Lucy for five seconds, hide, ask what it is for and what plays next.
2. First run: from `/` to the first valid play with no help, including an invalid folder path; time it; note the privacy wording on first run.
3. Make a Mix on `/mixes`: choose a card, then Play, Edit first or Save as draft; customise the shape; record hesitation and confidence.
4. Listen: ask what Next and Skip will do and what a pending request means.
5. My Mixes and Edit: identify playing, saved, queued and rendering; find a named draft; edit 2, 20 and 100-song mixes; reorder, audition, Studio, undo, export.
6. Requests and Discover: explain bridge consent and the word-connection phrase.
7. Library `/library` and Lucy `/mixes/lucy`: browse, retrieve a known song, ask Lucy for a mix and approve it.
8. Workshop: find one blocker on `/workshop` and its fix; recover from a stopped server mid-edit (injected faults: see `web/e2e/mp-0297-loading-and-recovery.e2e.ts`).
9. Phone participants (where tasks say mobile): the same cards on a real phone.
10. Read the cards word for word; the only help allowed is "What would you try?".

**Pass:** Raw counts per cohort (done unaided, stalled, gave up, wrong result) with denominators, timings and confidence 1 to 5, against thresholds fixed before the study. Observations stay separate from hypotheses.

**Record:** A study report per programme, with participant codes only, reviewed by someone who did not run the sessions; defects filed with route, step, expected, seen and severity.

Tracker: [tracker/user-study.md](tracker/user-study.md)

## Sitting 6: Staging, drills and rollback

Things that need a running deployment or a deliberate failure: the Cloud staging environment, game day, takedown drills, and local rollback and server-loss drills on a copy of your home.

**Before you start:**

- Staging config: `infra/cloudflare/env/staging.tfvars` and `staging.backend.hcl`; topology in `docs/adr/adr-0409-hosting-topology-and-environments.md` and `docs/saas/13-hosting-and-cost.md`.
- A copy of your Selecta home for the local drills, and an older checkout for rollback.

**Steps:**

1. Deploy: set up the GitHub OIDC credential broker (`infra/deploy/oidc_credentials.sh`), required reviewers on the `production` environment and the repository variables; run `.github/workflows/deploy.yml` to staging by workflow_dispatch; `infra/deploy/smoke.py` must pass.
2. Worker image: run `pip list` and `ffmpeg -buildconf` in the built image and compare with `docs/saas/licence-register.md`; record the GPU image's CUDA build.
3. Game day: follow `docs/operations/game-day.md` with an operator and an observer; engage and release each of the nine controls in `docs/operations/emergency/`; file `docs/operations/drills/game-day-<date>.md`.
4. Takedown drill: send a test notice, log it (`POST /api/admin/takedowns`), act on it within 24 hours (`POST /api/admin/takedowns/{id}/act`), check the audit trail and the overdue flag.
5. Rollback: `python tests/rollback_check.py <older checkout>`; all three reports must match (known differences are in `docs/acceptance.md`). Repeat on a copy of a real home.
6. Local failure drills: two Edge tabs on one server (switch draft then Apply in Studio; insert the same request twice); stop and restart the backend mid session; browse `/library` page 200+ during `uv run selecta analyse`; export with the disk full; a UNC path (`\\host\share\Music`) in the welcome screen.
7. Restore: back up from `/workshop/storage` and restore known drafts, ratings and overrides on a home copy.

**Pass:** A green staging run with production waiting for reviewers; drill records with times, every step in the audit log; rollback reports match; one insertion, stale Apply refused, no lost draft.

**Record:** Drill records under `docs/operations/drills/`, rollback output attached to the release report, and the programme's evidence file.

Tracker: [tracker/staging.md](tracker/staging.md)

## Sitting 8: Sign-off pass

Reading and deciding: approve decisions, audit evidence documents and code reviews, and give release dispositions. A task that says "independent" needs a reviewer who did not build it; you can sign owner decisions yourself.

**Before you start:**

- The programme ledgers: `docs/adr/selecta-4-evidence.md`, `selecta-3-1-evidence.md`, `selecta-experience-evidence.md`, `selecta-creative-interface-implementation-evidence.md`, `selecta-flow-implementation-evidence.md`, and the release-gate files (`selecta-4-release-gates.md`, `selecta-flow-release-gates.md`, `selecta-experience-release-gates.md`).
- Confirm the CI run for the exact SHA is green (`gh run list --branch <branch>`).

**Steps:**

1. Part A, first: approve the decisions and thresholds other sittings depend on: study thresholds and protocols (UF-0367-04, SF-0198-07), P0/P1 thresholds (SF-0240-08), the supported browser and OS matrix (P0121), the preservation contract (S3-0047-03), charters and ADR decisions.
2. Evidence-document audits: crosswalks, inventories, parity and verification matrices. Open the document and the checklist line, sample the claims against the code, record what you checked.
3. Independent code and test reviews, by area (Studio and Requests, Discover, Library, Workspace and Export, blind study, accessibility and architecture): read the tests named in the Evidence field and the cited source, and confirm the Acceptance text is really tested.
4. Owner walk-throughs: run `python tests/e2e_server.py 8799`, open each feature the line names and confirm it behaves as its tests say.
5. Privacy reviews: copy the diagnostics from `/workshop/diagnostics` and read the payload for paths and song names; watch the Edge Network panel during analysis.
6. Wording reviews: toasts, glossary (`web/src/ui/glossaryTerms.ts`) and consent text.
7. Part B, last: release dispositions per programme at one SHA: zero P0, every P1 accepted or fixed, a rollback plan (`tests/rollback_check.py`), and a written GO or NO-GO from you and an independent reviewer.

**Pass:** Each task carries the reviewer's name, the date and the SHA in its evidence row; Verified is set only by that reviewer.

**Record:** The programme's evidence file and, for releases, its release-gate file.
