# LF14 integration — zone-scoped local-first Rooms

## Integration state and scope

Agent 14 implements the opt-in metadata-only Rooms boundary, local availability validation, conservative local scheduling receipts, guest and host status projections, and test probes. **Not live by default.** Existing standalone/cloud Rooms use the previous library/planner when `RoomPorts.local_first` is absent. Pairing, QR codes, nicknames, staff approvals, votes, duplicate requests, display pairing, rate limits, and room closure remain on the original endpoints. There is no hosted audio fallback in local-first mode.

The local bridge is a **protocol interface**, not a substitute for Agents 07 and 09. No worker, venue scheduler, command transport, or database migration was changed. Do not enable the mode for customers until those dependencies and the integration/release gates below are verified.

## Contracts for integration owners

In `src/selecta/rooms/local_first.py`, `LocalRoomsBridge` exposes:

- `speaker(workspace_id, zone_id) -> LocalSpeaker | None`: fresh heartbeat (45 seconds; 5-second clock tolerance), correct workspace+zone, nonempty device/policy revision, fencing generation, physical output readiness, and absolute committed-until timestamp. **Online cloud state alone is insufficient.**
- `count_requestable(workspace_id, zone_id, crate, clean_only)` and `search(workspace_id, zone_id, query, limit)`, `track(...song_id)`, `describe(...song_ids)`: metadata-only snapshots with `LocalTrack` scope, `RecordingState.READY`, permitted/explicit flags, and fresh verification. Return only minimal `SongSummary(song_id, title, artist, length_s)`. **Never** return file paths, hashes, PCM, stems, fingerprints, signed URLs, or binaries. The Rooms boundary independently filters every returned item to the requested tenant/zone, validity and clean-only policy.
- `now_playing(workspace_id, zone_id) -> LocalNowPlaying | None`: generation-fenced zone-specific speaker read model. If it is not fresh and scoped, Rooms shows nothing, not potentially another speaker's playback.
- `schedule(workspace_id, zone_id, room_id, request_id, song_id, *, expected_generation, not_before, policy_revision) -> LocalScheduleReceipt | None`: idempotent on `(workspace_id, zone_id, request_id)`. **Agent 09** validates source/rights, playback graph, zones, transition feasibility and existing committed horizon at execution time. Schedule no earlier than `max(clock_now, committed_until)`, never cut into the committed/playing window. **Agent 07** ensures authenticated delivery, device authorization, expiration, generation fencing and durable acknowledgments; an HTTP 202 or command delivery is *not* an engine schedule. Only a matching acknowledged `LocalScheduleReceipt` allows the room to store the opaque operation ID.
- `progress(workspace_id, zone_id, operation_id) -> LocalProgress | None` and `cancel(...)`: only authenticated device-observed outcomes. `PLAYED` is persisted only through `record_outcome(..., "played")` **when** the trusted local progress reads `LocalStage.PLAYED`. Cancellation is advisory and never claims a committed local transition was undone.

These are Python dependency-injected ports. Wire the bridge through `RoomPorts(local_first=implementation)` where `rooms.wiring.install` constructs the service. The existing `NoCloudLibrary` and `NoCloudPlanner` remain safe defaults. Real implementations must persist and authenticate local-operation state and reconcile after disconnect; they must not use an unverified cloud cache as a readiness authority.

## Guest request state machine

The existing database `room_requests.status` values are preserved for migration compatibility. `stage` is an **additive public read model**, not a new database enum:

| Existing state/evidence | `stage` shown to guests | Meaning |
| --- | --- | --- |
| guest request before host approval (`sent`) | `awaiting_moderation` | Recorded; host has not approved |
| host approved / auto-approved without local ack | `accepted` | **Cloud acceptance only**; scheduling unconfirmed |
| approved while speaker offline/stale | `deferred` | Accepted but local execution cannot be verified |
| matching durable engine schedule receipt | `locally_scheduled` | Device accepted a request after policy/horizon preflight |
| trusted local progress `PREPARED` | `prepared` | Engine reports local preparation |
| confirmed `PLAYED` callback + matching local progress | `played` | Playback actually observed by device |
| host passes | `rejected` | Rejected by host |
| guest withdraws before local acknowledgment | `withdrawn` | Never scheduled |
| uncommitted request expires / room closes | `expired` | Pending request expires; already-acknowledged local operations retain their true state |
| no fit, media disappeared/blocked or planner unavailable | `deferred` | Explicit reason in guest status text |

`request_stage` is intentionally conservative. It cannot promote `PLAYED` just because a cloud planner claims it completed. Local operation IDs are kept as strings in the existing `song_request_id` field for compatibility; engines must reject collisions, enforce scoped idempotency and keep true immutable operation history.

`RoomSettings.zone_id` (default `main`) and `clean_only` (default `false`) are JSON settings, no schema change. A running local-first room **cannot switch zones**: close and recreate it so guests do not migrate to a different speaker silently. Explicit-blocked, missing, disconnected, stale, wrong-zone and non-permitted recordings cannot be requested; if the song disappears after host approval, the local handoff becomes unfit/deferred instead of being scheduled. UI labels distinguish **Accepted guest requests** from a confirmed upcoming playback list.


A live room cannot enable clean-only restrictions while already-acknowledged local requests are outstanding. Removing a source or banning a guest after the engine has acknowledged an operation requests local cancellation but does not falsely mark that operation withdrawn until an authoritative outcome arrives. The room displays such affected requests as deferred and preserves the possibility of a truthful later playback report.

## Access/privacy boundaries

- Guest endpoints still require a room-bound HttpOnly/SameSite cookie, check allowed origins on writes, and enforce per-guest/IP/room rate limits. Rejoining with the same valid token retains the nickname; an expired/rotated code cannot admit new guests; closure invalidates requests. Guests receive no workspaces, private catalogues, local media, identities, device paths or signed URLs.
- Any local-first catalogue summary must have the requested exact workspace+zone, fresh `READY` state, permitted status and (if enabled) non-explicit variant. Titles and artists are constrained to printable bounded strings; URLs, path-like strings and malformed duration are discarded. Guest DTOs are constructed from `SongSummary`, never serialized directly from local engine objects.
- Engine availability is **not** a guarantee that a guest can play a track: the speaker verifies the actual legal/rights and output policy on each schedule request. Cloud-side acceptance is never a playback instruction.
- Rate limits in `rooms/limits.py` remain a per-process backstop; retain edge rate limits, WAF, and workspace-scoped durable quotas for 500+ guest flood scenarios. Never loosen them to handle transient venue disconnect.
- If cloud remains reachable but venue goes offline, host may continue to moderate, but no new local schedules will be acknowledged until a fresh speaker is back. No direct cloud audio execution or emergency hosted playback bypass.

## Rollout and rollback

1. Merge Agent 07/09 dependencies **after** their independent CI; implement authenticated `LocalRoomsBridge` with strict zone scope, durable idempotent operations and playback acknowledgement.
2. Under a feature/configuration gate, explicitly inject `RoomPorts.local_first` only for migrated venues; keep all older standalone tenants on legacy ports until migration is completed. No file/blob path may cross that bridge.
3. Canary in clean-only and ordinary rooms, exercise disconnect/reconnect, committed windows, stale device generations, blocked and unavailable media, 500 guests, room rotations and membership isolation.
4. On trouble disable bridge for new rooms and/or stop accepting new requests; **do not switch an active migrated room back to hosted audio**, reinterpret an acknowledged local operation as a cloud planner job, or silently replay it. Preserve existing room request/history rows and wait for authoritative local recovery.
5. Advance rollout only after independent release/signoff evidence. Existing cloud audio infrastructure may be retired only by the separate migration/retirement gates.

**Known limitations:** The exact end-to-end local scheduling and device telemetry adapters are owned by Agents 09/07 and are not implemented here. No dedicated migrations were added (Agent 04 owns Alembic). `RoomSettings` uses existing JSON columns. Cross-process delivery reconciliation and durable per-request expiry sweeps require venue integration. The local-first sweep does not auto-end a room merely because its engine's cloud heartbeat is missing; it may still be playing offline. A truly verified `LocalNowPlaying` must be supplied by the bridge; otherwise the UI deliberately shows no local now-playing music. Public lyrics/audio transport remain out of scope. All actual source/media remains on the local venue engine.
