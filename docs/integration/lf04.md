## Storage, compatibility and concurrency

v1 Cloud mixes remain readable through the original five Cloud mix routes, with unchanged request/response shapes and protected immutable **mix_revision** artifact manifests. Version 2 is opt-in on those SAME routes: JSON body schema_version=2 for POST or ?schema_version=2 for GET. This avoids touching another agent's feature-flag registry.

v2 revisions use protected, zero-byte, content-addressed **lf_recipe_revision** manifests in the already-migrated artifacts table. They store metadata and opaque recording references only: never audio, device paths, raw fingerprints, local bindings or cloud-hosted media keys. Every occurrence has an independent stable occurrence_id, so duplicate tracks preserve separate identities. Cues have explicit source_seconds or beats timebases; transitions declare intent, not a trusted render.

An old v1 revision is exposed as a *read-only virtual v2 view* with explicit unresolved legacy_asset_id. Do not synthesize canonical_track_id or silently map an unmatched live/remaster/radio-edit recording. The original legacy revision remains the optimistic-concurrency token until a v2 edit is committed. Legacy and v2 history remains readable; restore creates a new immutable child, never rewriting the source revision.

Writes lock the workspace row (PostgreSQL SELECT FOR UPDATE, SQLite BEGIN IMMEDIATE) and compare base_revision with the latest actual persisted head. Two offline editors of one base produce one accepted edit and one 409 stale_revision. Legacy editing after v2 adoption refuses with 409 recipe_upgrade_required, so mixed clients cannot fork the head. Validation errors and failed writes roll back.

**No Alembic migration is needed by LF04:** existing artifacts already provide tenant-scoped unique (workspace_id, kind, input_hash) protected manifests. Agent 04 remains the sole owner of any future *shared schema migration*. Agents 03 and 17 must coordinate canonical reference, mapping, uniqueness and tenant/RLS requirements with Agent 04 before a new schema is introduced.

## Versioned endpoint contract

- GET /api/cloud-mixes?schema_version=2 returns recipes instead of the v1 mixes listing.
- POST /api/cloud-mixes with schema_version=2, name and occurrences array creates a portable recipe. Each occurrence contains occurrence_id, canonical_track_id, and optional title, artist and recording_version. No file or upload is required.
- GET /api/cloud-mixes/{mix_id}?schema_version=2 returns recipe, actual head_revision, full historical revision index and legacy_read_only_view.
- GET the same URL with &target_device_id=device-b adds per-device availability. Without a configured resolver, results are Unknown.
- POST /api/cloud-mixes/{mix_id}/revisions with schema_version=2, base_revision, changes and optional restore creates a new revision. Changes may include name, occurrences, cues, transitions and draft.
- Existing endpoints, response shapes and MIXES_READ / MIXES_EDIT authorization remain intact when schema_version is omitted.

## Required eight-song scenario

Device A saves eight distinct occurrences, occ0 through occ7. Device B sends a fresh, authorised, workspace- and device-scoped binding report: occ0–occ4 Ready; occ5/occ6 Missing; occ7 Candidate. The response counts are exactly ready=5, missing=2, candidate=1, version_mismatch=0, blocked=0, unknown=0. can_run is false. Candidate never becomes Ready through a title or metadata match. Order, cues, transition intentions and the immutable recipe revision are preserved. When the report expires, all eight become Unknown, not Missing or Ready.

Ready, Missing, Candidate, Version Mismatch, Blocked and Unknown are distinct wire states. Recording-version changes mark affected analysis, cues and adjacent transitions for revalidation. Even if every recording is Ready, transitions stay requires_local_rebuild until a separate local-engine preflight is integrated.

## Cross-agent interfaces

**Agent 03 — catalogue:** Implement the RecordingResolver Protocol, returning DeviceInventory(workspace_id, target_device_id, verified_at, expires_at, bindings, policy_version), with one DeviceBinding per known canonical track. Enforce device/workspace permission and never return filesystem paths, local hashes or audio. Canonical IDs are workspace-scoped opaque identities independent of legacy asset IDs; verify recordings locally and make candidates explicit.

**Agent 06 / Agent 09 — local artifacts and venue:** Validate cue timebase, source recording revisions and transitions locally before producing sound. A future transition certificate should be scoped to recipe revision, occurrence pair, device, source revisions, policy and expiry; until then nothing claims transitions are prepared.

**Agent 07 / Agent 08 — control:** Commands must carry an immutable recipe revision and playback ownership generation. Metadata readiness is not a device takeover or audio execution grant.

**Agent 17 — migration:** Consume the original immutable mix_revision artifacts and the pure from_legacy conversion helper. Implement tenant-scoped, idempotent legacy-asset-to-canonical-reference backfill with an explicit unresolved state and no guessed substitutions. Inventory R2, backups and asset retirement in Agent 17's owned paths, not here. Re-running a failed mapping must not mutate history or invent media.
