## Context and evidence boundary

Capacity must grow by starting more workers, on more than one provider, without exploding database connections or trusting worker clocks.

This ADR records a proposed decision. Nothing in it is implemented or measured yet; numbers come from the proposal and must be re-checked when the work starts.

## Decision

- Workers hold no database or storage credentials; they use a worker gateway (`register`, long-poll `claim`, `heartbeat`, `progress`, `complete`, `fail`) with short-lived pool-scoped tokens, and touch storage only through signed URLs from their claim.
- The gateway is a separate deployment from the customer API (same image), so worker traffic can't starve customers. Long-polls never hold a database connection; wake-ups use `LISTEN/NOTIFY` on a direct connection with jittered, partial wake-ups and a periodic re-check.
- The claim response carries the attempt's signed input URLs, attempt-scoped output slots, lease, fencing token and the flag decisions the job needs.
- Pools by capability: cpu-light, cpu-heavy, gpu (stems), export. Exports run in their own pool. Speculative attempts can be preempted across accounts by waiting interactive work and never take a pool's last free slot.
- Worker placement follows data transfer: every output upload is egress from the worker's host. Beta runs all workers on Modal in an EU region (CPU and GPU); a reserved CPU pool on Hetzner shared-vCPU servers is added when steady load justifies it; workers do not run on Render (25 GB included egress, $0.15/GB beyond).
- Autoscaling (run by the maintenance leader) uses outstanding estimated work-seconds over target drain time and p95 wait, with per-pool min/max, daily spend ceilings, and a warm worker in the seam and stems pools only while someone is listening.

## User outcome and acceptance contract

Adding a worker means starting a container with pool settings and a credential; nothing else changes.

## Rejected alternatives

- Workers connecting to Postgres directly (connection storms, credentials everywhere).
- Push dispatch to fixed worker addresses.

## Implementation checklist - 1/7 Implemented; 6/7 In progress; 0/7 Not started; 0/7 independently Verified

1. **SC-0396-01 - Gateway endpoints.** **Acceptance:** All six endpoints exist with token auth and idempotency. **Required verification:** Integration tests. **Implementation:** Implemented; standalone `selecta gateway` service, scoped tokens, fenced lifecycle routes and signed object URLs. **Evidence:** `tests/test_worker_gateway_api.py`, `src/selecta/gateway_cloud.py`, `src/selecta/work/gateway_api.py`; **Independently Verified:** No.
2. **SC-0396-02 - Worker image.** **Acceptance:** Linux image with ffmpeg, torch CPU and pinned models runs analysis and renders end to end. **Required verification:** Staging smoke test. **Implementation:** In progress; built `services/worker/Dockerfile` (Python 3.12.10 slim, ffmpeg, `uv sync --frozen --no-dev` with CPU-only torch, non-root user, no baked secrets, an entry point that re-checks the weights before starting `selecta.workers.cloud`) and `services/worker/models.lock.json`, which pins the beat_this small0 weights by SHA-256 and size; `selecta.workers.model_lock` downloads, checks and refuses any changed or oversized file, and only lists models the licence register allows in cloud mode. On 2026-11-11 the base image was pinned by its Docker Hub index digest (`python:3.12.10-slim-bookworm@sha256:fd95fa22...88db`, test now requires a digest) and `selecta.workers.engine_handlers` added Cloud handlers for `analyse.song` (the engine's `analyse_audio`, publishing `analysis.npz` with the beat grid, features and summary), `seam.render` (`choose_transition` over two analysis artifacts, publishing `seam.flac`) and `export.render` (`render_set`, publishing `mix.flac`); each reads inputs by key through `ctx.open_input` (or the gateway's named inputs), checks every source's SHA-256, normalises it with a local-files-only ffmpeg, and publishes with provenance through `ctx.publish` (the worker's ArtifactStore or the gateway slot); `selecta.workers.cloud` registers only the handlers of its `SELECTA_WORKER_POOL`. Key detection uses the chroma fallback in Cloud because S-KEY isn't pinned. Needs staging: build the image in CI, pin weights for lyric alignment (wav2vec2) when its handler lands, and run the staging smoke test end to end. **Evidence:** `tests/test_cloud_engine_handlers.py` (11 passed locally on 2026-11-11, synthetic songs through a real `JobContext` on `LocalArtifactStore`); `tests/test_cloud_worker_image.py` (15 passed on 2026-11-11); `tests/test_cloud_runner_audio.py`; `services/worker/Dockerfile`; `services/worker/models.lock.json`; `src/selecta/workers/model_lock.py`; `src/selecta/workers/engine_handlers.py`. **Independently Verified:** No.
3. **SC-0396-03 - GPU pool.** **Acceptance:** Demucs windows run on Modal with CPU fallback when GPU capacity is absent. **Required verification:** Staging test; timing recorded. **Implementation:** In progress; `infra/workers/pools.json` gives the gpu pool a T4 primary and a CPU fallback, and `selecta.work.autoscale.decide` switches to the fallback when the provider reports no GPU capacity, sizes the pool for the fallback's slower speed and raises an alert. On 2026-11-11 `selecta.work.autoscale_leader` hooked the autoscaler into the maintenance leader (task `autoscale`, every 30 s, flag `cloud.autoscale`): each tick reads outstanding work, the p95 queued wait, live workers and listeners from the database, decides per pool, records alerts and calls a `Launcher`; `ModalLauncher` scales the deployed function `worker-{pool}` (or `worker-{pool}-fallback`) with `update_autoscaler`, stops the other launch, treats a refused GPU scale-up as no capacity so the next tick falls back to CPU, and is inert unless `SELECTA_MODAL_APP` and a Modal token are set (then `selecta maintain` names the missing settings). Day spend is estimated from the sizes the leader set and restarts on failover, so Modal's own spend limit stays the hard stop. Needs staging: deploy the Modal app definitions, run Demucs windows on a Modal GPU and on the fallback with timings recorded; Demucs is still under licence review (ADR-0405), so it is not in the worker image yet. **Evidence:** `tests/test_cloud_autoscale_leader.py` (fake launcher and fake Modal lookup) with `tests/test_cloud_maintenance_service.py` (25 passed on 2026-11-11, SQLite and local PostgreSQL); `tests/test_cloud_autoscale.py::test_no_gpu_capacity_falls_back_to_cpu_workers_and_says_so`; `src/selecta/work/autoscale.py`; `src/selecta/work/autoscale_leader.py`; `infra/workers/pools.json`. **Independently Verified:** No.
4. **SC-0396-04 - Scale-out.** **Acceptance:** Throughput rises monotonically with worker count to a documented bottleneck. **Required verification:** Worker scaling benchmark 1→32. **Implementation:** In progress; `tests/load/worker_scaling.py` runs N workers through claim, start and complete, reports jobs per second for each N and names the first count whose gain is under 10% as the bottleneck; a small SQLite run proves the harness. Needs staging: the 1 to 32 benchmark with real Cloud workers through the gateway on PostgreSQL, with the bottleneck written into docs/saas/15-stress-testing.md (a local 1 to 32 run could not get a test slot on the shared laptop). **Evidence:** `tests/test_cloud_worker_scaling.py` (8 passed locally on 2026-11-10); `tests/load/worker_scaling.py`. **Independently Verified:** No.
5. **SC-0396-05 - Spend ceilings.** **Acceptance:** A pool stops scaling at its ceiling and alerts. **Required verification:** Staging test with a low ceiling. **Implementation:** In progress; `selecta.work.autoscale.decide` sizes each pool from outstanding estimated work-seconds over its drain target (plus one when p95 wait is over target), keeps a warm worker only while someone listens, and never goes past max or what is left of the daily spend ceiling, alerting whenever either holds it back; the ceiling beats min and warm workers; pool limits and ceilings are code in `infra/workers/pools.json`. Needs staging: wire the decision into the maintenance leader with a Modal launcher, today's spend and an alert sink, then the staging test with a low ceiling. **Evidence:** `tests/test_cloud_autoscale.py` (12 passed locally on SQLite on 2026-11-10, including the Hypothesis property that workers never pass max or the ceiling and always alert when held back); `src/selecta/work/autoscale.py`. **Independently Verified:** No.
6. **SC-0396-06 - Gateway isolation.** **Acceptance:** A worker storm on the gateway leaves customer API p95 unchanged. **Required verification:** Load test. **Implementation:** In progress; the gateway has its own app factory and `selecta gateway` entry point, and the load test is written: `tests/load/k6/gateway_storm.js` browses the customer API with and without a worker storm of registrations and claims on the gateway, and `tests/load/compare_p95.py` fails if customers' p95 under the storm is more than 10% and 20 ms worse. Needs staging: deploy the gateway separately and run the baseline and storm against staging. **Evidence:** `tests/test_cloud_worker_scaling.py::test_the_storm_uses_only_routes_the_api_and_gateway_serve` and the compare tests (8 passed locally on 2026-11-10). **Independently Verified:** No.
7. **SC-0396-07 - Egress measured.** **Acceptance:** Bytes uploaded per job type are recorded and match the cost model. **Required verification:** Phase 0 benchmark and staging metrics. **Implementation:** In progress; `selecta.work.egress` sums the bytes of published artifacts by the job type that made them over a time window and compares the averages with `infra/workers/egress_model.json` (25% tolerance; a type without a number is reported, never passed). Needs staging: the Phase 0 real-audio benchmark to fill the model, and the comparison against staging metrics. **Evidence:** `tests/test_cloud_worker_egress.py` (3 passed locally on SQLite on 2026-11-10); `src/selecta/work/egress.py`. **Independently Verified:** No.
